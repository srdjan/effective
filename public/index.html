What Effective is

Effective is a small functional language designed to transpile to Effect-TS.

Effective combines immutable data, arrow functions, pattern matching, and typed service operations. A program reads like direct TypeScript, while each function contract records expected failures and required capabilities.

The transpiler turns each contract into an Effect-TS type. A function that returns A, fails with E, and uses R becomes Effect.Effect<A, E, R>.

Services become Context services, and providers become Layer values. Records, errors, and brands become Schema declarations. Options become Option values.

The transpiler targets the effect core modules and selected modules from the Effect ecosystem. The table names each module and its role.

Effect-TS moduleRole in transpiled code
effect: Effect, Context, Layer, Option, SchemaComputations, services, providers, options, records, errors, and brands. The examples use these modules now.
effect/http, FileSystem, and @effect/platform-node, -bun, or -browserHTTP and file services, and the runtime for each host.
effect/sql and a driver such as @effect/sql-pgDatabase services.
@effect/opentelemetryExport of traces, metrics, and logs.

Version 0 specifies the core mapping. Bindings for the HTTP, file, SQL, and telemetry modules need later specifications. A typed host module will expose them as Effective services.

Version 0 has a Deno transpiler and CLI in the effective-lang repository. The Effect-TS examples in this book are manually written; this site does not run Effective code.

The transpiler boundary is a typed intermediate representation, or IR. Each expression records its type, execution mode, failures, requirements, and source position. The Effect-TS backend translates checked IR into TypeScript.

Effective separates domain failures from defects and cancellation. A missing user can be data. Invalid safe-integer arithmetic is a defect. A typed catch handles only declared domain failures.

Three facts describe each function call. The result type describes normal completion. The failure set names expected errors. The requirement set names service methods.

These facts travel through composition. A caller must account for expected failures and required capabilities. Execution mode separately records whether invocation performs effects.

This book first explains values and contracts. It then develops one Users service across lookup, update, recovery, retry, and provision. A payment pipeline joins the concepts near the end.

Values and types

Every Effective binding and aggregate value is immutable.

This chapter uses a separate example module. Chapter 4 starts the shared Users domain with UserId, an alias of string.

A const binding cannot change. A record update creates a new record and preserves the old value. Effective has no assignment, class inheritance, or implicit receiver.

A brand gives nominal identity to a base value. UserId("u1") creates the brand, but it performs no validation. The unbrand builtin converts the value back to string.

Ordinary type aliases use structural equality. Two records with equal fields are compatible. Brands and errors use declaration identity, which prevents accidental substitution.

A signature names declared types. A primitive type such as string or int can occur only inside a type or error declaration. So this module declares type Label = string and uses Label in signatures.

A brand of a record, such as Brand<{ name: Name }>, gives the record declaration identity, as a brand of a primitive does. Two values of one numeric brand accept comparisons, addition, and subtraction.

An optional field read returns Option<T>. Some(value) represents presence, and None represents absence. This rule prevents an absent field from becoming an unchecked undefined value.

Match expressions require complete coverage. Every arm produces a compatible result type. A never branch, such as fail(error), fits any result type.

The int type contains finite safe integers. Addition, subtraction, and multiplication can defect when the result is invalid. Division always returns number.

Records reject missing required fields and unknown fields. A record update evaluates its base once, then evaluates update fields from left to right.

Function contracts

A function contract states its success type, expected failures, and required service methods.

The examples in this chapter use the User, StoreUnavailable, and Users declarations from chapter 4. Chapter 4 defines each shared declaration.

The result type remains Option<User>. A service call performs its operation when the running function reaches the call. The source type never becomes Effect<Option<User>, E, R>.

A declared failure is an expected outcome. A required capability records a call to one service method. A service name in uses expands to every method in that service.

Calls propagate the declared contract of the callee. The declared sets can exceed the body sets, but they cannot omit a body effect.

A result annotation closes the contract. An omitted fails clause means no expected failures. An omitted uses clause means no service requirements. The body cannot exceed either set.

Local functions can omit result annotations and infer their result and effects. Exported functions require parameter and result annotations. Parameters also require annotations without a contextual function type.

Execution mode is separate from failure and requirement sets. A provider can remove every requirement while the computation remains effectful. Empty sets can therefore describe either execution mode.

Creating an arrow function is pure. Calling that function runs its body each time. Unbodied source function types default to effect execution in version 0.

Nonempty failure or requirement sets imply effect execution. Empty sets do not imply purity. The transpiler must preserve the independently inferred execution mode.

A block returns its final expression. Effective source has no return statement. Ordered expressions run from left to right, and only the selected branch runs.

One domain, two languages

The Users domain provides the shared declarations for the next four chapters.

Effective service declarations contain method signatures. Service methods have no this binding. Each method remains a distinct capability after name resolution.

A service method lists only failures from that operation. Method requirement sets are empty. A host provider can have separate acquisition failures and dependencies.

Users.find, Users.save, and Users.all are separate capabilities. A contract can name one method without declaring the other methods. Static tracking does not sandbox host adapters.

The Effect-TS tab represents successful values inside Effect.Effect. Its error parameter contains tagged errors. Its requirement parameter contains the Users service when a function accesses that context.

Later TypeScript examples assume these imports, schemas, errors, and the Users class. Later Effective examples assume the declarations above. Each Effect-TS tab shows intended translation, not generated output.

Effect-TS tracks the whole Users service in its requirement type. Effective retains each method requirement in checked IR or backend metadata.

These isolated translations use short error tags and service keys. A transpiler backend must encode resolved identities in tags, keys, and brand tokens across modules.

Lookup and update

Small functions keep service operations, domain decisions, and record changes separate.

The first function converts None into a named domain failure. The second function changes a value. The third function sequences lookup, change, and save.

fail(error) ends the normal path and contributes the error identity. Errors are nominal, so declarations with equal fields remain different error types.

The match reads the option once and selects one arm. The None arm constructs UserMissing with the requested identifier. StoreUnavailable remains unchanged.

Effective uses one direct call syntax for pure functions and service methods. The checked call still distinguishes an ordinary call from a service operation in typed IR.

The block evaluates each binding and expression in order. A failure stops the remaining steps. The final active value becomes the successful result.

Pipelines and collections

A pipeline passes its left value as the first argument of each stage.

The runtime evaluates the left side once. It then evaluates the stage callee and explicit arguments. Pipelines associate from left to right.

A stage can name a local function, imported function, builtin, or declared service method. Version 0 excludes placeholders, currying, inline lambda stages, and record-member stages.

The prelude provides map, filter, and fold. Each builtin traverses from left to right. Map and filter preserve order, while fold carries one accumulator.

Map and filter call their callback once for each visited element. Empty inputs produce empty outputs. Fold returns its initial accumulator for an empty input.

Each callback must be pure and have empty failure and requirement sets. Contextual inline arrows work because the builtin supplies their parameter types. Known pure functions also work.

A callback that provides its own service can still execute effects. Empty failures and requirements do not make that callback pure. Execution mode closes this loophole.

The checker specializes each builtin use to a closed function type before IR serialization. Version 0 does not expose the builtin type variables to users.

Exercise

Why can version 0 reject a callback parameter whose source type only shows empty effect sets?

Show the answer

An unbodied function type defaults to effect execution. Version 0 has no source annotation that requires pure execution.

Recovery and provision

Effective controls an operation through explicit syntax and deferred zero-argument functions.

A typed catch handles matching failures from its protected block. Unhandled failures continue to the caller. Catch does not intercept defects or cancellation.

retry requires a deferred operation. The function below runs its first attempt and allows two more attempts. Each attempt can perform the Users.find operation again.

Passing Users.find(id) directly would run the call before retry took control. Effective never inserts suspension because a parameter expects a deferred function.

Retry preserves the callback result, failures, and requirements. Retry itself has effect execution mode. Its times value must be a finite, nonnegative safe integer literal in version 0.

The host maps its provider registration to users-live.js in the Effect-TS tab. Effective source keeps the registered host:providers import.

These provider examples assume UsersLive is a Layer<Users> with infallible acquisition and no dependencies. A fallible provider adds its acquisition failures and requirements to the result.

Providing Users removes the Users requirement. The operation still uses effect execution mode. Version 0 receives provider values from typed host modules and defines no layer construction syntax.

Exercise

Why do retry and provide require () => operation() instead of operation()?

Show the answer

The zero-argument function defers execution. The controlling builtin can choose when and how often to invoke the operation.

A payment pipeline

The payment workflow composes effectful and pure stages through one data-first pipeline.

The pipeline stops at the first expected failure. chargeOrder retries only the charge call. saveOrder cannot run after a missing order or declined payment.

The uses Orders clause expands to Orders.find and Orders.save. Payments.charge stays method-specific. The resulting contract exposes only the needed service surface.

The charge service can repeat an external action. The application author must decide whether the provider makes repeated charges safe, such as through idempotency.

The Effect-TS tab uses a schema to check safe integers at a boundary. Effective separately requires its checker and runtime to preserve int arithmetic rules.

The Effect-TS tab uses Effect.gen for ordered operations. Effective keeps the same order through final-expression blocks and pipeline stages. The source contract presents plain Order as its success type.

Modules and typed IR

Modules expose named declarations and keep host integration behind typed interfaces.

Version 0 permits named imports from relative .eff files and registered host modules. It excludes default imports, namespace imports, renaming, re-exports, and package resolution.

Module constants require pure initializers. Imports cannot run application service operations. A host starts execution through an entry function after it supplies required providers.

The transpiler will parse source, resolve identities, infer effects, check contracts, specialize builtins, and emit typed IR. Its Effect-TS backend then emits TypeScript from that IR. The current project defines these stages but supplies no transpiler.

Resolution assigns stable identities to types, errors, services, capabilities, values, and locals. Equal names in different modules do not identify the same declaration.

Source formMeaning
A fails E uses RA function succeeds with A, can fail with E, and requires R.

The IR resolves every reference to a stable identity. It separates ordinary calls from service operations. It preserves retry, provide, catch, brands, and source positions as explicit nodes.

A pipeline needs no IR node. Lowering creates fresh bindings and ordinary call or service-operation nodes. This preserves single evaluation, stage order, and useful diagnostic positions.

Acceptance fixtures must cover evaluation order, branch selection, failure propagation, contract rejection, closure deferral, retry, and provider resolution. Pipeline fixtures must also check stage identity.
