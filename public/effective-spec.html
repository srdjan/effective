Status and scope

Effective is a small functional language designed to transpile to Effect-TS. Immutable values, ordinary functions, and explicit contracts define its source style.

The transpiler targets the effect core modules and selected modules from the Effect ecosystem. The section on typed IR and backends names each module.

This reference defines language core version 0. The documentation edition is draft 0.1, dated October 15, 2026.

The package contains a specification, teaching examples, and a TypeScript model of typed intermediate representation, or IR. It contains no Effective transpiler or runtime.

Rules in this reference describe intended language behavior. The examples are manually authored. Effect-TS tabs illustrate the intended transpiler output; a transpiler did not generate them.

Effective files use the .eff extension. Earlier .lft files remain provisional artifacts from the design discussion.

The core covers data, functions, services, failures, pipelines, retry, providers, and named modules. Later sections identify features outside this core.

Effective uses familiar TypeScript shapes but adds language forms. A TypeScript parser cannot parse Effective source directly.

A first example

An error declaration creates a nominal tagged error type and a constructor. Nominal identity means the declaration determines which error the value represents.

A service declaration names external operations. Each service method is a capability, which is a statically tracked requirement for calling that operation.

The log function returns void, can fail with ConsoleUnavailable, and requires Console.print. Its call runs in the current source execution context.

Service declarations use method notation. Function values and function type annotations use arrows. Methods have no implicit receiver or this binding.

The source return type names the successful value. It does not name an Effect object. The target backend supplies its own execution representation.

Source and lexical rules

Source text uses UTF-8. Source positions in IR count UTF-16 code units, with an exclusive end offset.

Identifiers start with an ASCII letter, underscore, or dollar sign. Later characters may also contain decimal digits. Names are case-sensitive.

Line comments start with //. Block comments use /* and */ and do not nest. Comments do not produce runtime values.

Strings use double quotes with JSON escape sequences. String interpolation, single-quoted strings, and template literals are outside the initial lexical core.

Numeric literals use decimal notation, with optional fraction and exponent parts. Literal values must be finite. Integral literals infer int unless context requires number.

The parser recognizes |> before |. The first token denotes a pipeline; the second separates type alternatives and effect-set members.

A newline or semicolon separates declarations, service methods, and block items. Commas separate record fields, arguments, parameters, and match arms.

A newline continues an incomplete expression. It also continues a signature before fails, uses, or its final arrow, and an expression before |>.

The core does not apply general JavaScript semicolon insertion. Parentheses make grouping explicit when a multiline form would otherwise be unclear.

Data and types

Source typeMeaning
stringA string value.
booleantrue or false.
intA finite JavaScript safe integer.
numberA host numeric value; source numeric literals must be finite.
voidThe unit result of an operation.
neverNo successful value, as with fail.
unknownA value that needs a checked boundary before typed use.
T[]An immutable array of T values.
[A, B]An immutable tuple with the stated positions.
Option<T>Some(value) or None.
A | BA union of alternatives.
Brand<T>A nominal type whose representation is T.

Type aliases use structural compatibility. Brands and errors retain declaration identity. The checker rejects recursive type definitions in version 0.

Record fields are required unless the field name has ?. Reading an optional field returns Option<T>.

A required field of type Option<T> differs from an optional field of type T. A future codec backend must preserve that difference.

Record construction rejects missing required fields, duplicate fields, and unknown fields. Contextual typing preserves expected literal alternatives.

Record updates construct a new value. One spread may appear first, followed by replacement fields. The original record remains unchanged.

OrderId("o1") constructs a brand value when OrderId has base type string. A brand adds identity, not an automatic validation predicate.

unbrand(value) explicitly returns the base value. The checker does not silently discard nominal identity.

The checker treats int as a subtype of number. Division returns number. An int result outside the safe range is a runtime defect.

Equality compares compatible primitives, literal unions, and primitive brands. Comparing records requires a named comparison function.

Conditions require boolean. Effective does not use JavaScript truthiness. void cannot appear in a record field, array, or tuple.

Functions and blocks

Every binding and aggregate value is immutable. Effective has no assignment operator, mutable let binding, implicit receiver, or source class declaration.

Parameters and calls use ordinary argument lists. Effective does not insert currying, partial application, or callback execution.

An arrow with one expression uses that expression as its result. A block uses its final expression as its result.

A block that ends with a binding, or contains no items, produces void. A final void operation also produces void.

Effective has no return statement in version 0. Function blocks and other expression blocks use the same result rule.

A brace after an arrow begins a block. Parentheses distinguish a returned record, as in ({ ...user, active: true }).

Creating an arrow evaluates no part of its body. Calling the arrow runs the body again. Captured immutable values retain ordinary lexical scope.

Exported functions require parameter and result annotations. Local parameters require annotations unless a contextual function type supplies their types.

A local function without a result annotation infers its result and effect sets. A result annotation creates a closed failure and requirement contract.

For a closed contract, omitted fails means no expected failures. Omitted uses means no unprovided capability requirements.

Those omissions do not assert pure execution. The checker tracks execution mode separately, including effects whose providers are already supplied.

A function type without a body defaults to effect execution. Imported interfaces retain their resolved execution modes.

Version 0 has no source annotation for pure callback parameters. Known pure functions and contextual inline callbacks still work with pure collection builtins.

Services and contracts

fails names a closed set of expected error identities. uses names a closed set of required service methods.

A whole service name expands to all methods in that service. Method requirements retain resolved identities across module boundaries.

A service method declaration has no uses clause. Its own invocation adds that method capability to the caller requirements.

A host provider captures implementation dependencies. The method interface describes only parameters, success, and expected failures.

The checker verifies that inferred body failures and requirements fit the declared sets. A body cannot silently widen an explicit contract.

A declared set may be wider than the body needs. Calls through that interface propagate the declared sets.

Error constructors produce tagged data. The field name _tag is reserved for generated error tags.

Static capability tracking does not itself prompt for permission or sandbox a host adapter. The host supplies implementations that honor the declared contracts.

Execution order and mode

Ordinary calls evaluate the callee once, then arguments from left to right, then invoke the function. Fields and bindings evaluate from left to right.

A record update evaluates its base once before replacement fields. Only the selected if, match, or short-circuit branch executes.

The checker combines effects from all statically reachable paths. Source execution is sequential unless a future explicit concurrency feature changes that rule.

Each expression has an execution mode: pure or effect. Each function type records the mode that applies when the function runs.

Nonempty failure or requirement sets require effect mode. Empty sets permit either mode. Closing a requirement set through provision does not remove execution effects.

A closure expression is pure even when its function type describes effectful invocation. Module initialization checks the expression mode, not the latent function mode.

Mode propagation uses logical OR over callee evaluation, arguments, invoked functions, and reachable branches.

An explicit contract with nonempty sets lifts a pure body into an effectful function interface. A pure function may lift into an effectful callback interface.

An effectful function cannot satisfy a pure callback requirement. Lifting wraps execution; it does not invoke a callback during construction.

Recursive functions require explicit signatures. Mode inference starts pure and propagates intrinsic effects and effectful calls until the recursive group reaches a fixed point.

Expected failure stops the current normal path. Defects and cancellation use separate runtime outcomes and do not enter ordinary typed recovery.

Pipelines and collections

A pipeline passes its left result as the first argument of the next stage. The stages associate from left to right.

The first form invokes transform(value). The second invokes transform(value, a, b). Neither form creates a partially applied function.

Each stage first evaluates the left value once. It then evaluates the resolved callee and explicit arguments, and finally invokes the stage.

A temporary binding preserves this order during lowering. Direct textual substitution into an ordinary call could change the callee evaluation order.

Stage names may resolve to local, imported, or builtin functions. Dotted stages must identify declared service methods.

Version 0 excludes inline lambda stages, placeholders, spread arguments, and runtime record-member stages.

The pipeline operator has lower precedence than arithmetic, comparisons, and boolean operators. Parentheses may override grouping.

The prelude supplies map, filter, and fold. Their callbacks require pure execution mode and empty failure and requirement sets.

map transforms each element. filter selects elements through a boolean predicate. Both visit elements once from left to right and preserve order.

fold(items, initial, callback) invokes callback(state, item) from left to right. Its result retains the accumulator type. An empty array returns initial.

Empty arrays produce empty results for map and filter. A defect stops traversal. Effectful traversal remains outside version 0.

An unbodied callback parameter defaults to effect mode. It cannot pass the pure collection callback check, even when its effect sets are empty.

The transpiler specializes builtin rules before IR serialization. Each distinct closed builtin type receives a unique synthetic ValueId and a closed prelude interface.

Pattern matching

if requires a boolean condition and an else branch. Branch results require a common result type. never fits every successful result type.

Match subjects evaluate once. The checker requires complete coverage and rejects unreachable arms and constructors that do not belong to the subject type.

Supported patterns include literals, _, Some(binding), None, nominal error bindings, and a string discriminator in a tagged record.

Matching an unbounded primitive domain requires a final wildcard. Nested patterns are outside version 0.

A spread binding in this pattern captures the whole narrowed record. It does not mean JavaScript rest destructuring.

A tagged pattern without a binding lowers with a null binding. Pattern-bound values remain immutable and local to their arm.

Failure and recovery

fail(error) produces no normal value. Its success type is never, and its failure set includes the nominal error identity.

catch installs handlers before evaluating the protected block. It removes handled tags and combines the handlers failures and requirements.

Successful and handled paths require a common result type. Unhandled tags continue to the caller.

The checker rejects duplicate handlers and handlers for tags absent from the protected failure set. It does not treat defects as typed failures.

A backend may use Result data or a typed failure channel. It must not implement domain failures as untyped JavaScript exceptions.

Retry and providers

This fragment assumes the payment module defines pay, id has type OrderId, and the host supplies AppLive. The fragment belongs inside a function.

These control functions require a zero-argument function. They receive work that has not run yet. Ordinary expected parameter types never insert suspension.

retry invokes its callback for the first attempt and again after each permitted typed failure. times counts retries after the first attempt.

Version 0 requires a finite nonnegative safe integer literal for times. Defects and cancellation do not trigger typed retry.

Retry retains the callback result type, failures, and requirements. The author must choose operations that tolerate repeated execution.

A provider value lists supplied capabilities, acquisition mode, acquisition failures, and acquisition dependencies. Host modules supply provider values in version 0.

provide installs the provider while invoking its callback. Provider acquisition runs before the callback and may contribute additional failures and requirements.

Provision removes supplied callback requirements and adds acquisition dependencies. It preserves typed failures from both acquisition and callback execution.

Provider lookup occurs at invocation time. Creating a closure does not freeze the current provider environment.

retry, provide, fail, and catch have effect execution mode in the core. A provider with empty acquisition sets can still require effectful acquisition.

Source layer construction, resource scopes, and concurrency need separate rules. This reference does not infer those rules from the Effect target.

Modules and boundaries

This boundary imports the supplied users module. UsersLive supplies Users with no acquisition failure or additional dependency.

Imports select named exports from relative files or registered host modules. Version 0 excludes default imports, namespaces, renaming, re-exports, and package resolution.

Prefix export exposes a declaration by name. Interfaces also carry the complete supporting type graph, without importing private names into the local source scope.

The checker resolves declaration identities before checking bodies. Identical printed names from separate modules never share identity merely because their spellings match.

Module initialization may construct immutable data and closures. It cannot run service operations or other effectful initializers.

The linker rejects module dependency cycles. Application execution begins when the host invokes an exported entry function with the required providers.

A host registry supplies interfaces for host: modules. This registry is host configuration, not arbitrary JavaScript import access inside Effective.

Host adapters must validate boundary values and preserve immutable source data. Registered implementations must honor their declared errors, capabilities, and execution behavior.

Typed IR and backends

The accompanying typed-ir.ts defines the proposed payload model. It is a structural TypeScript model, not an implementation of the transpiler or validator.

The internal format marker remains light-functional-ir, version 1. Effective branding does not change that existing wire contract.

Every expression records its type, active failure and requirement sets, execution mode, and source span. Function types retain invocation effects and mode.

References use resolved identities. Service operations use perform nodes; ordinary function invocations use call nodes.

Pipelines lower through fresh block bindings and existing calls. A generated binding uses the left expression span; calls retain the corresponding stage span.

Diagnostics refer to source expressions and hide temporary names. Source positions count UTF-16 units, with the end position excluded.

The IR retains explicit retry, provide, catch, brand, and unbrand operations. A backend must not replace deferred control with eager helper calls.

Pure exports return ordinary target values. Effectful exports return target computations, even when their error and requirement sets are both empty.

The Effect-TS backend uses Effect.Effect<A, E, R>, Context services, and typed failures. Its R parameter groups requirements by service rather than individual method.

The backend preserves method precision in checked IR or metadata. A coarser target type does not erase the source contract.

A backend must encode resolved declaration identities in error tags, service keys, and brand tokens. Equal printed names from different modules must remain distinct.

Records, errors, and brands become Schema declarations. Options become Option values. Providers become Layer values.

The backend targets the effect core modules and selected modules from the Effect ecosystem. The table names each module and its role.

Effect-TS moduleRole in transpiled code
effect: Effect, Context, Layer, Option, SchemaComputations, services, providers, options, records, errors, and brands. The examples use these modules now.
effect/http, FileSystem, and @effect/platform-node, -bun, or -browserHTTP and file services, and the runtime for each host.
effect/sql and a driver such as @effect/sql-pgDatabase services.
@effect/opentelemetryExport of traces, metrics, and logs.

Version 0 specifies the core mapping. Bindings for the HTTP, file, SQL, and telemetry modules need later specifications. A typed host module will expose them as Effective services.

The manual log fixture retains its original log.lft source identifier. Its semantic payload illustrates the same method declaration now shown in log.eff.

Equations and validation

F(expression) denotes active expected failures. R(expression) denotes active capability requirements. Both sets contain resolved identities.

Execution mode combines the modes of evaluated children, branches, and invocations. Nonempty sets require effect mode. Empty sets do not establish purity.

A semantic validator must recompute annotations and reject disagreements. TypeScript checks payload shape but cannot prove the semantic equations.

The validator receives immutable source texts keyed by source identifiers. It uses those texts to check source positions.

Validation areaRequired check
IdentityReferences, imports, exports, and capabilities resolve in their scopes.
TypesArguments, fields, branches, and function results match their checked types.
ContractsFunction bodies fit declared failures and requirements.
ExecutionModes preserve invocation effects, closure deferral, and provider acquisition.
RecoveryHandlers select possible tags and return compatible results.
ControlRetry jobs and provider jobs are zero-argument functions. Counts satisfy the literal constraint.
InitializationModule constants have pure active execution and empty active sets.
SerializationSets are sorted and unique. Literals are finite. Source spans refer to supplied text.

Surface grammar

This grammar summarizes the named extensions. The lexical rules and type rules above constrain the terminal forms. It is not a generated parser.

The checker recognizes only the stated core. Unlisted JavaScript features do not become valid merely because the file resembles TypeScript.

The core operators are +, -, *, /, ===, !==, <, <=, >, >=, &&, and ||. Their operands follow the primitive typing rules.

Types use postfix [] for arrays and brackets for tuples. Option<T> and Brand<T> are the initial builtin type applications.

A brace after an arrow, if condition, else, try, or catch enters its declared control context. Returned object literals require parentheses after an arrow.

The checker rejects duplicate declarations, fields, methods, match arms, and handler tags where their scopes require uniqueness.

Operator group, highest firstOperand and result rules
Calls and field readsA call checks parameter types. A field read uses the declared field type.
* and /Numeric operands produce a numeric result. Division produces number.
+ and -Numeric operands produce a numeric result. Addition also accepts two strings and produces string.
<, <=, >, >=Numeric operands produce boolean.
=== and !==Compatible primitives, literal unions, or matching primitive brands produce boolean.
&&Boolean operands produce boolean, with short-circuit evaluation.
||Boolean operands produce boolean, with short-circuit evaluation.
|>The stage receives the left result as its first argument.

Binary operators within each group associate from left to right. Numeric arithmetic preserves int when both operands are int, except for division.

Arithmetic with a number operand produces number. String addition performs no implicit conversion. Invalid int arithmetic produces a defect.

Diagnostics and conformance

Diagnostics identify a source span, a category, and a concrete mismatch. Suggested categories include syntax, unknown-name, type-mismatch, failure-contract, requirement-contract, and execution-mode.

These categories describe the proposed diagnostic contract. No delivered transpiler emits them yet.

Acceptance fixtures must check evaluation order, single evaluation, branch selection, failure propagation, explicit contracts, closure deferral, retry, and provider resolution.

Pipeline fixtures must verify argument placement, stage order, short-circuiting after failure, and source locations for generated bindings.

Collection fixtures must verify callback purity, order, empty arrays, and distinct closed builtin identities.

Backend fixtures must compare values, typed failures, and operation traces. A future Effect target also requires strict TypeScript checking and runtime checks.

Delivered checks cover document consistency, the manual log IR fixture, and strict TypeScript checks of every illustrative Effect-TS tab. No Effective execution or translation-equivalence check exists.

Deferred features include user generics, effect-row polymorphism, source purity assertions, resource scopes, concurrency, streams, mutable references, macros, and recursive schemas.

Deferral does not imply that those features need new syntax. Each extension must preserve the current execution, failure, and capability distinctions.

Sources and lineage

Forma inspired the separation of success values, expected failures, and required capabilities. Effective chooses a TypeScript-family functional surface for those ideas.

Source references: https://forma-lang.com/effect and https://forma-lang.com/effect/reference.

Direct-call design reference: https://forma-lang.com/rfcs/0003-direct-style-effects. That RFC described proposed behavior when the design research occurred.

Target references: https://effect.website/docs/v4/api/effect/Context and https://effect.website/docs/v4/error-management/expected-errors.

These references support the design lineage and target examples. They do not establish an Effective implementation.
