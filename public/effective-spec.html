Status and scope

Effective is a small functional language designed to transpile to Effect-TS. Immutable values, ordinary functions, and explicit contracts define its source style.

The transpiler targets the effect core modules and selected modules from the Effect ecosystem. The section on typed IR and backends names each module.

This reference defines language core version 1. The documentation edition is draft 0.23, dated October 18, 2026.

Core 1 specifies additional source features in stages. The compiler implements the documented core 1 subset, including references, races, buffered and merged streams, source Layers, and unbounded traversal. The validation report identifies which examples run.

Draft 0.2 adds three rules. A primitive type can occur only inside a type or error declaration. A brand of a record type is a nominal record. Two values of one numeric brand accept comparisons, addition, and subtraction.

This site contains a specification, teaching examples, and a TypeScript model of typed intermediate representation, or IR. The site does not run the Effective compiler; a Deno transpiler and CLI exist in the effective-lang repository.

Rules in this reference describe intended language behavior. The examples are manually authored. Effect-TS tabs illustrate the intended transpiler output; a transpiler did not generate them.

Effective files use the .eff extension. Earlier .lft files remain provisional artifacts from the design discussion.

The core covers data, functions, services, failures, pipelines, retry, providers, named modules, and the core 1 extensions. Later sections identify deferred features.

Effective uses familiar TypeScript shapes but adds language forms. A TypeScript parser cannot parse Effective source directly.

A first example

An error declaration creates a nominal tagged error type and a constructor. Nominal identity means the declaration determines which error the value represents.

A service declaration names external operations. Each service method is a capability, which is a statically tracked requirement for calling that operation.

The log function returns void, can fail with ConsoleUnavailable, and requires Console.print. Its call runs in the current source execution context.

Service declarations use method notation. Function values and function type annotations use arrows. Methods have no implicit receiver or this binding.

The source return type names the successful value. It does not name an Effect object. The target backend supplies its own execution representation.

Source and lexical rules

Source text uses UTF-8. Source positions in IR count UTF-16 code units, with an exclusive end offset.

Identifiers start with an ASCII letter, underscore, or dollar sign. Later characters may also contain decimal digits. Names are case-sensitive.

Line comments start with //. Block comments use /* and */ and do not nest. Comments do not produce runtime values.

Strings use double quotes with JSON escape sequences. String interpolation, single-quoted strings, and template literals are outside the initial lexical core.

Numeric literals use decimal notation, with optional fraction and exponent parts. Literal values must be finite. Integral literals infer int unless context requires number.

The parser recognizes |> before |. The first token denotes a pipeline; the second separates type alternatives and effect-set members.

A newline or semicolon separates declarations, service methods, and block items. Commas separate record fields, arguments, parameters, and match arms.

A newline continues an incomplete expression. It also continues a signature before fails, uses, or its final arrow, and an expression before |>.

The core does not apply general JavaScript semicolon insertion. Parentheses make grouping explicit when a multiline form would otherwise be unclear.

Data and types

Source typeMeaning

T[]An immutable array of T values.

Option<T>Some(value) or None.
A | BA union of alternatives.
Brand<T>A nominal type whose representation is T.

Type aliases use structural compatibility. Brands and errors retain declaration identity. The checker rejects recursive type definitions in version 0.

A primitive type is string, int, number, boolean, or a literal type such as "paid" or 1. A primitive type can occur only inside the body of a type or error declaration. All other positions use declared type names. These positions include parameters, results, service methods, constant annotations, local annotations, and function types.

void, never, and unknown are not primitive types for this rule. Option<T>, T[], tuples, records, unions, function types, Effect, Stream, and Sink stay valid in any position when their parts are declared types. The rule also applies to a host interface file (.effi), which declares the services and providers of a host. The checker reports declaration/013 for each primitive type in another position.

An alias such as type Name = string satisfies the rule. An alias adds a name but not identity. Brand<T> adds identity.

Record fields are required unless the field name has ?. Reading an optional field returns Option<T>.

A required field of type Option<T> differs from an optional field of type T. A future codec backend must preserve that difference.

Record construction rejects missing required fields, duplicate fields, and unknown fields. Contextual typing preserves expected literal alternatives.

Record updates construct a new value. One spread may appear first, followed by replacement fields. The original record remains unchanged.

A bracket expression constructs an immutable list. An expected tuple type requires the exact element count and checks each element against its position. Otherwise an expected array type checks every element against its element type. Without an expected type, a nonempty homogeneous list infers an array after literal widening. An empty list or elements without a common array element type require a contextual type. A trailing comma is allowed.

List elements evaluate once from left to right. A failed element stops evaluation. Their active failures and requirements combine in the list expression. The typed IR retains whether the expression is an array or tuple; the Effect backend emits a JavaScript array for either shape.

OrderId("o1") constructs a brand value when OrderId has base type string. A brand adds identity, not an automatic validation predicate.

unbrand(value) explicitly returns the base value. The checker does not silently discard nominal identity.

A brand of a record type is a nominal record. Account({ ... }) constructs the value and checks the record against the base type. A record literal without that call does not fit Account. A field read reads the field of the base record. A record update keeps the brand, so { ...account, active: false } has type Account.

Two nominal records with identical fields are different types. Version 0 does not match a record pattern against a nominal record. It also rejects a nominal record as the operation record of withResource.

The checker treats int as a subtype of number. Division returns number. An int result outside the safe range is a runtime defect.

A numeric brand has the base type int or number, after aliases. The operators <, <=, >, and >= accept two values of one numeric brand. The operators + and - accept two values of one numeric brand and produce that brand. An int brand result outside the safe range is a defect, as for int.

The operators * and / do not accept a brand, because the product of two amounts is not an amount. A string brand does not accept +. These operations need unbrand first. A literal operand needs the brand call, as in total + Cents(50).

Equality compares compatible primitives, literal unions, and primitive brands. Comparing records, nominal records included, requires a named comparison function.

Conditions require boolean. Effective does not use JavaScript truthiness. void cannot appear in a record field, array, or tuple.

Effect<A, E, R> is an immutable computation value. A is its successful result type. E is never or a union of nominal error names. R is never or a union of qualified service methods. Omitted E and R mean never. These channels describe deferred execution, not the effects of evaluating an expression that produces the value. Effect values may be bound, passed, and returned.

Effect value compatibility checks the successful result covariantly and permits source failure and requirement sets that are subsets of the expected sets. Nominal error and method identities are retained. A value with more possible failures or requirements cannot fit a narrower declared Effect type.

Functions and blocks

Every binding and aggregate value is immutable. Effective has no assignment operator, mutable let binding, implicit receiver, or source class declaration.

Parameters and calls use ordinary argument lists. Effective does not insert currying, partial application, or callback execution.

An arrow with one expression uses that expression as its result. A block uses its final expression as its result.

A block that ends with a binding, or contains no items, produces void. A final void operation also produces void.

Effective has no return statement in version 0. Function blocks and other expression blocks use the same result rule.

A brace after an arrow begins a block. Parentheses distinguish a returned record, as in ({ ...user, active: true }).

Creating an arrow evaluates no part of its body. Calling the arrow runs the body again. Captured immutable values retain ordinary lexical scope.

Exported functions require parameter and result annotations. Each annotation follows the rule on primitive types in Data and types. Local parameters require annotations unless a contextual function type supplies their types.

A local function without a result annotation infers its result and effect sets. A result annotation creates a closed failure and requirement contract.

For a closed contract, omitted fails means no expected failures. Omitted uses means no unprovided capability requirements.

Those omissions do not assert pure execution. The checker tracks execution mode separately, including effects whose providers are already supplied.

A function type without a body defaults to effect execution. Imported interfaces retain their resolved execution modes.

Version 0 has no source annotation for pure callback parameters. Known pure functions and contextual inline callbacks still work with pure collection builtins.

Services and contracts

fails names a closed set of expected error identities. uses names a closed set of required service methods.

A whole service name expands to all methods in that service. Method requirements retain resolved identities across module boundaries.

A service method declaration has no uses clause. Its own invocation adds that method capability to the caller requirements.

A host provider captures implementation dependencies. The method interface describes only parameters, success, and expected failures.

The checker verifies that inferred body failures and requirements fit the declared sets. A body cannot silently widen an explicit contract.

A declared set may be wider than the body needs. Calls through that interface propagate the declared sets.

Error constructors produce tagged data. The field name _tag is reserved for generated error tags.

Static capability tracking does not itself prompt for permission or sandbox a host adapter. The host supplies implementations that honor the declared contracts.

Execution order and mode

Ordinary calls evaluate the callee once, then arguments from left to right, then invoke the function. Fields and bindings evaluate from left to right.

A record update evaluates its base once before replacement fields. Only the selected if, match, or short-circuit branch executes.

The checker combines effects from all statically reachable paths. Source execution is sequential except for explicit concurrent operations. The traverse concurrency option states its limit and cancellation behavior.

Each expression has an execution mode: pure or effect. Each function type records the mode that applies when the function runs.

Nonempty failure or requirement sets require effect mode. Empty sets permit either mode. Closing a requirement set through provision does not remove execution effects.

A closure expression is pure even when its function type describes effectful invocation. Module initialization checks the expression mode, not the latent function mode.

Mode propagation uses logical OR over callee evaluation, arguments, invoked functions, and reachable branches.

An explicit contract with nonempty sets lifts a pure body into an effectful function interface. A pure function may lift into an effectful callback interface.

An effectful function cannot satisfy a pure callback requirement. Lifting wraps execution; it does not invoke a callback during construction.

Recursive functions require explicit signatures. Mode inference starts pure and propagates intrinsic effects and effectful calls until the recursive group reaches a fixed point.

defer(job) accepts a zero-argument function and constructs an Effect value from its invocation result, failure set, and requirement set. The job body does not run during construction. Evaluating the job expression may contribute its own active effects. run(value) accepts an Effect value and executes its deferred computation anew on every call. Its active effects combine evaluation of value with the value’s deferred failures and requirements. run has effect execution mode even when those sets are empty.

Expected failure stops the current normal path. Defects and cancellation use separate runtime outcomes and do not enter ordinary typed recovery.

Pipelines and collections

A pipeline passes its left result as the first argument of the next stage. The stages associate from left to right.

The first form invokes transform(value). The second invokes transform(value, a, b). Neither form creates a partially applied function.

Each stage first evaluates the left value once. It then evaluates the resolved callee and explicit arguments, and finally invokes the stage.

A temporary binding preserves this order during lowering. Direct textual substitution into an ordinary call could change the callee evaluation order.

Stage names may resolve to local, imported, or builtin functions. Dotted stages must identify declared service methods.

Version 0 excludes inline lambda stages, placeholders, spread arguments, and runtime record-member stages.

The pipeline operator has lower precedence than arithmetic, comparisons, and boolean operators. Parentheses may override grouping.

The prelude supplies map, filter, fold, and traverse. The callbacks of map, filter, and fold require pure execution mode and empty failure and requirement sets. The callback of traverse may be pure or effectful.

map transforms each element. filter selects elements through a boolean predicate. Both visit elements once from left to right and preserve order.

fold(items, initial, callback) invokes callback(state, item) from left to right. Its result retains the accumulator type. An empty array returns initial.

Empty arrays produce empty results for map and filter. A defect stops traversal.

traverse(items, callback) invokes the callback once per item from left to right and returns an array in input order. It is effectful even when the callback is pure. Its active failure and requirement sets include those of callback invocation. An empty array invokes no callbacks. Without options, the Effect backend uses sequential Effect.forEach, and a typed callback failure prevents later callbacks from starting. An optional third argument must be the literal record { concurrency: N } or { concurrency: "unbounded" }, where N is a positive safe integer. A numeric bound runs at most N callbacks simultaneously; "unbounded" starts every callback without a concurrency limit. Both modes return results in input order. A typed failure starts no queued callbacks in bounded mode, interrupts active siblings in either mode, and waits for their scoped finalizers; explicit interruption also waits for finalizers. The backend passes the literal concurrency option to Effect.forEach. A pure callback is lifted into an Effect callback. Dynamic concurrency values and other option fields are rejected.

all(effects, options?) executes a tuple, record, or array of Effect values and returns the same shape filled with their results. It unions their typed failures and service requirements. The default is sequential. An optional literal { concurrency: N } uses a positive safe integer limit; { concurrency: "unbounded" } has no limit. Concurrent success results retain input positions and record keys. A typed failure interrupts active siblings and waits for their finalizers. A heterogeneous bracket literal needs a contextual tuple type before passing to all. Other option fields and dynamic concurrency values are rejected. The backend uses Effect.all. A source binding named all shadows the prelude operation.

partitionAll(jobs, options?) accepts a homogeneous array of Effect<A,E,R> values. It runs every job and returns [A[], E[]], with successes and typed errors in separate input-order arrays. The operation has no typed failure channel and requires the jobs' combined services. A job defect or interruption still terminates the collection. The default is sequential; the optional concurrency record has the same literal rule as all. The backend uses Effect.partition. A source binding named partitionAll shadows the prelude operation.

validateAll(jobs, onErrors, options?) accepts a homogeneous array of Effect<A,E,R> values and a pure one-argument callback from E[] to a nominal error B. It evaluates every job. If all succeed, it returns A[] in input order. If any job fails, it discards successes and fails with the callback's B value; the callback receives every typed error in input order, and its array is nonempty at runtime. The source type remains E[] because core 1 has no nonempty-array type. The operation requires R and fails only with B; defects and interruption still terminate it. The default is sequential, and the optional literal concurrency record follows all. The backend uses Effect.validate followed by Effect.mapError. A source binding named validateAll shadows the prelude operation.

allResults(effects, options?) accepts an Effect tuple, record, or homogeneous array. It runs every member and preserves the input shape, position, or key. Each result is the tagged record union { _tag: "Success", success: A } | { _tag: "Failure", failure: E } for that member's A and E; an error in one member does not stop the others. The collection has no typed failure channel and requires the members' combined services. Defects and interruption still terminate it. The default is sequential; the optional concurrency record follows all. The backend uses Effect.all with mode: "result". A source binding named allResults shadows the prelude operation.

Stream<A,E,R> is a deferred producer and Sink<I,O,E,R> is a deferred consumer. Their failure and requirement sets describe execution, not construction. unfold(seed, callback) takes an inline arrow returning Option<[A, State]>; None ends the stream. mapEffect(stream, callback) takes an inline effectful arrow and combines deferred channels. sinkForEach(callback) takes an inline effectful arrow with an annotated input and produces void. These operations use direct call syntax. runStream(stream, sink) activates both values and combines their channels.

Stream operations use one-element pull demand without prefetch or concurrent mapping. The producer does not run until runStream starts. The next pull follows consumer completion. A producer, transform, or consumer failure stops demand and waits for scoped finalizers; interruption also waits. The backend uses Stream.unfold, Stream.mapEffect, Sink.forEach, and Stream.run.

An unbodied callback parameter defaults to effect mode. It cannot pass the pure collection callback check, even when its effect sets are empty.

The transpiler specializes builtin rules before IR serialization. Each distinct closed builtin type receives a unique synthetic ValueId and a closed prelude interface.

Pattern matching

if requires a boolean condition and an else branch. Branch results require a common result type. never fits every successful result type.

Match subjects evaluate once. The checker requires complete coverage and rejects unreachable arms and constructors that do not belong to the subject type.

Supported patterns include literals, _, Some(binding), None, nominal error bindings, and a string discriminator in a tagged record.

Matching an unbounded primitive domain requires a final wildcard. Nested patterns are outside version 0.

A spread binding in this pattern captures the whole narrowed record. It does not mean JavaScript rest destructuring.

A tagged pattern without a binding lowers with a null binding. Pattern-bound values remain immutable and local to their arm.

Failure and recovery

fail(error) produces no normal value. Its success type is never, and its failure set includes the nominal error identity.

catch installs handlers before evaluating the protected block. It removes handled tags and combines the handlers failures and requirements.

Successful and handled paths require a common result type. Unhandled tags continue to the caller.

The checker rejects duplicate handlers and handlers for tags absent from the protected failure set. It does not treat defects as typed failures.

A backend may use Result data or a typed failure channel. It must not implement domain failures as untyped JavaScript exceptions.

Retry and providers

This fragment assumes the payment module defines pay, id has type OrderId, and the host supplies AppLive. The fragment belongs inside a function.

These control functions require a zero-argument function. They receive work that has not run yet. Ordinary expected parameter types never insert suspension.

retry invokes its callback for the first attempt and again after each permitted typed failure. times counts retries after the first attempt.

Version 0 requires a finite nonnegative safe integer literal for times. Defects and cancellation do not trigger typed retry.

Retry retains the callback result type, failures, and requirements. The author must choose operations that tolerate repeated execution.

A provider value lists supplied capabilities, acquisition mode, acquisition failures, and acquisition dependencies. Host modules supply provider values in version 0.

provide installs the provider while invoking its callback. Provider acquisition runs before the callback and may contribute additional failures and requirements.

Provision removes supplied callback requirements and adds acquisition dependencies. It preserves typed failures from both acquisition and callback execution.

Provider lookup occurs at invocation time. Creating a closure does not freeze the current provider environment.

retry, provide, fail, and catch have effect execution mode in the core. A provider with empty acquisition sets can still require effectful acquisition.

withResource(acquire, use, release) takes three inline closures. Acquisition has no parameters and returns an operation record with required function fields. Use and release each take that record as one parameter. The use result and operation arguments and results are data only: recursively no function, Effect value, provider, or unknown. Release returns void. A scoped parameter may occur only as the direct receiver of an operation call, such as file.read(); it cannot escape through a return, alias, aggregate, nested closure, or host argument. A field cannot be read as a value. Invocation failures and requirements of all three callbacks combine; execution is effectful even with empty sets. Release runs after success, failure, defect, or interruption, and its own typed failure remains in the result channel. Host adapters create operation records and remain responsible for their functions' behavior. Core 1 defines general borrowed handles, source Layers, races, and scoped fibers below.

Modules and boundaries

This boundary imports the supplied users module. UsersLive supplies Users with no acquisition failure or additional dependency.

Imports select named exports from relative files or registered host modules. Version 0 excludes default imports, namespaces, renaming, re-exports, and package resolution.

Prefix export exposes a declaration by name. Interfaces also carry the complete supporting type graph, without importing private names into the local source scope.

The checker resolves declaration identities before checking bodies. Identical printed names from separate modules never share identity merely because their spellings match.

Module initialization may construct immutable data and closures. It cannot run service operations or other effectful initializers.

The linker rejects module dependency cycles. Application execution begins when the host invokes an exported entry function with the required providers.

A host registry supplies interfaces for host: modules. This registry is host configuration, not arbitrary JavaScript import access inside Effective.

Host adapters must validate boundary values and preserve immutable source data. Registered implementations must honor their declared errors, capabilities, and execution behavior.

Typed IR and backends

The accompanying typed-ir.ts describes the current compiler payload model. The independent validator lives in the effective-lang repository.

Core 1 requires light-functional-ir version 2. The compiler, validator, and linked model now use version 2. Effective branding does not change the format marker.

Every expression records its type, active failure and requirement sets, execution mode, and source span. Function types retain invocation effects and mode.

References use resolved identities. Service operations use perform nodes; ordinary function invocations use call nodes.

Pipelines lower through fresh block bindings and existing calls. A generated binding uses the left expression span; calls retain the corresponding stage span.

Diagnostics refer to source expressions and hide temporary names. Source positions count UTF-16 units, with the end position excluded.

The IR retains explicit retry, provide, catch, brand, and unbrand operations. A backend must not replace deferred control with eager helper calls.

Pure exports return ordinary target values. Effectful exports return target computations, even when their error and requirement sets are both empty.

The Effect-TS backend uses Effect.Effect<A, E, R>, Context services, and typed failures. Its R parameter groups requirements by service rather than individual method.

The backend preserves method precision in checked IR or metadata. A coarser target type does not erase the source contract.

A backend must encode resolved declaration identities in error tags, service keys, and brand tokens. Equal printed names from different modules must remain distinct.

Records, errors, and brands become Schema declarations. Options become Option values. Providers become Layer values.

An Effect value maps to Effect.Effect<A, E, Rservice>, where Rservice is the union of service classes containing the required methods; checked IR keeps the precise method-level requirements. defer maps to Effect.suspend for an effectful callback, or a suspended pure-to-effect lift for a pure callback. run sequences the stored Effect value in the enclosing effect context. Neither operation supplies a provider.

The IR has distinct unfold, map-effect, sink-for-each, and run-stream expressions. Stream and Sink types carry deferred channels; run-stream activates them. The IR has a distinct with-resource expression carrying the three closures and the scoped parameter identities. Independent validation checks the operation-record shape, data-only types, scoped references, and invocation channels. The Effect-TS backend maps it to Effect.acquireUseRelease with suspended acquisition and Effect-returning use and release callbacks.

The backend targets the effect core modules and selected modules from the Effect ecosystem. The table names each module and its role.

Effect-TS moduleRole in transpiled code
effect: Effect, Context, Layer, Option, Schema, Stream, SinkComputations, services, providers, options, records, errors, brands, and incremental streams and sinks. The compiler emits these modules.
effect/http, FileSystem, and @effect/platform-node, -bun, or -browserHTTP and file services, and the runtime for each host.
effect/sql and a driver such as @effect/sql-pgDatabase services.

Core 0 specifies the existing mapping. Core 1 specifies one file service through a typed host adapter. HTTP, SQL, and telemetry adapters need separate specifications.

The manual log fixture retains its original log.lft source identifier. Its semantic payload illustrates the same method declaration now shown in log.eff.

Equations and validation

F(expression) denotes active expected failures. R(expression) denotes active capability requirements. Both sets contain resolved identities.

Execution mode combines the modes of evaluated children, branches, and invocations. Nonempty sets require effect mode. Empty sets do not establish purity.

A semantic validator must recompute annotations and reject disagreements. TypeScript checks payload shape but cannot prove the semantic equations.

The validator receives immutable source texts keyed by source identifiers. It uses those texts to check source positions.

Surface grammar

This grammar summarizes the named extensions. The lexical rules and type rules above constrain the terminal forms. It is not a generated parser.

The checker recognizes only the stated core. Unlisted JavaScript features do not become valid merely because the file resembles TypeScript.

The grammar accepts a primitive type in every type position. The checker then applies the rule on primitive types in Data and types.

The core operators are +, -, *, /, ===, !==, <, <=, >, >=, &&, and ||. Their operands follow the primitive typing rules and the numeric brand rule in Data and types.

Types use postfix [] for arrays and brackets for tuples. Option<T>, Brand<T>, and Effect<A, E, R> are builtin type applications.

Core 1 also reserves Ref<A>, Fiber<A,E>, RetrySchedule<E>, Codec<Decoded,Encoded>, and Layer<Services,E,R>. Their type arguments follow the same angle bracket and union rules.

Core 1 builtins are makeRef, getRef, setRef, updateRef, race, withFiber, joinFiber, interruptFiber, bufferStream, mergeStreams, retrySchedule, codec, decode, encode, layer, and mergeLayers. Draft 0.5 adds all for Effect collections. Draft 0.6 adds scoped and forkScoped. Draft 0.7 adds zipStreams. Draft 0.8 adds concatStreams. Draft 0.9 adds flatMapStreams. Draft 0.10 adds partitionAll. Draft 0.11 adds validateAll. Draft 0.12 adds allResults. Draft 0.13 adds takeStream. Draft 0.14 adds takeWhileStream. Draft 0.15 adds takeUntilStream. Draft 0.16 adds dropStream. Draft 0.17 adds dropWhileStream. Draft 0.18 adds filterStream. Draft 0.19 adds mapStream. Draft 0.20 adds scanStream. Draft 0.21 adds mapAccumStream. Draft 0.22 adds foldStream. Draft 0.23 adds foldEffectStream. They use ordinary call syntax.

The borrow parameter qualifier applies only in a function parameter list. An opaque type declaration applies only in a host interface file.

A brace after an arrow, if condition, else, try, or catch enters its declared control context. Returned object literals require parentheses after an arrow.

The checker rejects duplicate declarations, fields, methods, match arms, and handler tags where their scopes require uniqueness.

Diagnostics and conformance

Diagnostics identify a source span, a category, and a concrete mismatch. The categories are syntax, unknown-name, declaration, type-mismatch, pattern, failure-contract, requirement-contract, execution-mode, module, host-boundary, and validation.

The effective-lang compiler reports each diagnostic with a code that joins a category and a number, such as type-mismatch/003. A primitive type outside a type or error declaration gives declaration/013.

Acceptance fixtures must check evaluation order, single evaluation, branch selection, failure propagation, explicit contracts, closure deferral, retry, and provider resolution. Effect value fixtures must check construction without execution, repeated run, transport through bindings and functions, and failure and requirement contracts at the run boundary.

Pipeline fixtures must verify argument placement, stage order, short-circuiting after failure, and source locations for generated bindings.

Collection fixtures must verify callback purity for map, filter, and fold; callback effects for traverse; sequential, bounded, and unbounded concurrency, order, fail-fast sibling interruption, finalizer completion, empty arrays, and distinct closed builtin identities. Effect collection fixtures must also verify tuple and record shape, unioned channels, and cancellation. Stream fixtures must verify deferred construction, one-element demand, channel activation, and cancellation cleanup.

Backend fixtures must compare values, typed failures, and operation traces. A future Effect target also requires strict TypeScript checking and runtime checks.

Delivered checks cover document consistency, the manual log IR fixture, and strict TypeScript checks of every illustrative Effect-TS tab. The compiler repository checks emitted TypeScript and runtime behavior; this site checks its illustrative tabs separately.

Core 1 extensions

Core 1 adds the following source contracts. The compiler supports the listed reference, race, scoped fiber, borrowed handle, stream, retry schedule, codec, and source Layer forms. Drafts 0.4 and 0.5 extend concurrency with unbounded traverse and heterogeneous Effect collection. Target checks and runtime tests cover each slice.

References and concurrent effects

Ref<A> is a shared mutable cell inside an Effect runtime. makeRef(value), getRef(ref), setRef(ref, value), and updateRef(ref, callback) are effectful. The update callback is pure, and its replacement is atomic.

race(left, right) accepts two Effect values with compatible success types. It returns the first success, interrupts the loser, and waits for its finalizers. If both fail, the result has their union of typed failures.

withFiber(job, use) starts a supervised child from an Effect value. Its inline use callback receives a borrowed Fiber<A,E>. joinFiber exposes the child result and typed failures. interruptFiber stops it and waits for finalizers.

The child receives its service requirements when it starts. A child failure enters the parent contract when joined. The child is interrupted when use exits, even without a join.

forkScoped(job) starts an Effect value in the current scope and discards its Fiber handle. The job must have no typed failures. The call requires the reserved Scope capability and the job's service requirements. The child may outlive the spawning fiber; scope closure interrupts it and waits for finalizers. scoped(job) runs an Effect value in a fresh local scope, removes its Scope requirement, and closes the scope after success, failure, defect, or interruption. Its result and remaining channels come from the job. A source binding named scoped or forkScoped shadows the prelude operation. Raw Scope values and explicit Scope.close remain deferred.

Borrowed resources

A host interface may declare an opaque type. Effective may name that type but cannot inspect or construct its representation. Host type declarations must avoid import cycles with provider declarations.

withResource accepts an acquired handle as well as an operation record. Its use and release parameters are borrowed for that expression. They may pass the handle to a borrow-qualified parameter.

A host interface declares opaque type Name. A function parameter uses borrow name: Type to accept a scoped handle. Only host interfaces and functions whose bodies obey the borrow rule may declare such parameters.

A borrowed value cannot escape through a return, aggregate, alias, closure capture, or ordinary parameter. Borrow-qualified helpers cannot retain the value. Host methods promise the same rule at the trusted boundary.

Use and release results cannot contain the borrowed handle. Release runs after success, failure, defect, or interruption. Nested withResource calls compose scopes without exposing raw Scope values.

Buffered and merged streams

bufferStream(stream, { capacity: N }) creates a deferred stream with a positive safe integer literal N. It uses suspending backpressure. At most N elements wait in its queue, with one producer item in flight.

mergeStreams(left, right) accepts compatible element types. It starts both streams and ends after both finish. Each source keeps its own order; cross-source order is unspecified.

zipStreams(left, right) accepts any two Stream values and returns a Stream of ordered pairs [Left, Right]. It combines their deferred failure and service requirements. It starts production only on terminal consumption and ends when either input ends. An extra unpaired element is not emitted; closing the zipped stream interrupts the remaining producer and waits for its finalizers. A source binding named zipStreams shadows the prelude operation.

concatStreams(left, right) accepts two Stream values and returns a Stream whose element type is the union of their element types. It emits every left element before starting the right stream. The right stream is never started if the left stream fails. Construction is deferred until terminal consumption. Deferred failures and service requirements from both streams are combined. A source binding named concatStreams shadows the prelude operation.

flatMapStreams(source, callback) accepts a Stream and an inline pure callback from each source element to a Stream. It concatenates the inner streams in source order, exhausting one before starting the next. Construction does not pull either stream. The result carries the inner element type and the union of outer and inner deferred failure and service channels. A failure stops later inner streams; interruption closes the active inner stream and waits for its finalizers. Concurrent flatMap and switch behavior remain deferred. A source binding named flatMapStreams shadows the prelude operation.

takeStream(stream, count) accepts a Stream<A,E,R> and a pure Int count. It returns Stream<A,E,R> and emits at most the first count elements. A count at or below zero produces an empty stream without pulling the source. Construction does not pull the source; consuming a positive prefix closes upstream work when the limit ends. The count expression is evaluated when takeStream is called. The backend uses Stream.take. A source binding named takeStream shadows the prelude operation.

takeWhileStream(stream, predicate) accepts a Stream<A,E,R> and an inline pure one-argument predicate from A to boolean, with no failure or service channels. It returns Stream<A,E,R>. The source is pulled and the predicate is called only during terminal consumption. It emits the longest prefix for which the predicate returns true. The first false element is consumed but not emitted, and later elements are not pulled. A source error before that boundary propagates; after it, the source is not evaluated. Ending the prefix closes started upstream work and waits for its finalizers. The backend uses Stream.takeWhile. A source binding named takeWhileStream shadows the prelude operation.

takeUntilStream(stream, predicate) accepts a Stream<A,E,R> and an inline pure one-argument predicate from A to boolean, with no failure or service channels. It returns Stream<A,E,R>. The source is pulled and the predicate is called only during terminal consumption. It emits elements through the first element for which the predicate returns true, including that matching element, then stops without pulling later elements. If no element matches, it emits the entire source. A source error before a match propagates; after a match, the source is not evaluated. Ending at a match closes started upstream work and waits for its finalizers. The backend uses Stream.takeUntil without excludeLast. A source binding named takeUntilStream shadows the prelude operation.

dropStream(stream, count) accepts a Stream<A,E,R> and a pure Int count. It returns Stream<A,E,R>. A positive count consumes and discards up to that many source elements, then emits every remaining element. A zero or negative count emits the source unchanged. If the source ends before the count is reached, the result is empty. The count expression is evaluated when dropStream is called, but source pulls remain deferred until terminal consumption. A source failure in the discarded prefix still propagates. Started upstream work closes normally on completion, failure, or interruption. The backend uses Stream.drop. A source binding named dropStream shadows the prelude operation.

dropWhileStream(stream, predicate) accepts a Stream<A,E,R> and an inline pure one-argument predicate from A to boolean, with no failure or service channels. It returns Stream<A,E,R>. The source is pulled and the predicate is called only during terminal consumption. It discards the longest initial prefix for which the predicate returns true, then emits the first false element and every later element without testing the predicate again. If every element satisfies the predicate, the result is empty. A source failure in the discarded prefix still propagates. Started upstream work closes normally on completion, failure, or interruption. The backend uses Stream.dropWhile. A source binding named dropWhileStream shadows the prelude operation.

filterStream(stream, predicate) accepts a Stream<A,E,R> and an inline pure one-argument predicate from A to boolean, with no failure or service channels. It returns Stream<A,E,R>. The source is pulled and the predicate is called once for each element only during terminal consumption. It emits every element for which the predicate returns true, in source order, and consumes but omits the others. If no element matches, the result is empty. A source failure propagates even after rejected elements. Started upstream work closes normally on completion, failure, or interruption. The backend uses Stream.filter without type refinement. A source binding named filterStream shadows the prelude operation.

mapStream(stream, transform) accepts a Stream<A,E,R> and an inline pure one-argument callback from A to B, with no failure or service channels. It returns Stream<B,E,R>. The source is pulled and the callback is called once per element only during terminal consumption. It emits each transformed value in source order. A source failure propagates after earlier transformed values, and started upstream work closes normally on completion, failure, or interruption. The backend uses Stream.map without the index parameter. A source binding named mapStream shadows the prelude operation.

scanStream(stream, seed, update) accepts a Stream<A,E,R>, a pure seed expression of type S, and an inline pure two-argument callback from (S,A) to S, with no failure or service channels. It returns Stream<S,E,R>. Construction does not evaluate the seed expression or pull the source. Each terminal consumption evaluates the seed once and emits it before any source pull. It then calls update once per source element and emits each new state in source order. Each run starts with a fresh scan state. An empty source emits only the seed. A source failure propagates after states already emitted, and started upstream work closes normally on completion, failure, or interruption. The backend uses Stream.scan with a lazy seed function. A source binding named scanStream shadows the prelude operation.

mapAccumStream(stream, seed, update) accepts a Stream<A,E,R>, a pure seed expression of type S, and an inline pure two-argument callback from (S,A) to [S,B[]], with no failure or service channels. The callback declares its tuple result type explicitly so B is known even when an input emits no values. It returns Stream<B,E,R>. Construction does not evaluate the seed or pull the source. Each terminal consumption evaluates the seed once, starts with fresh state, calls update once per source element, and emits the returned array in order before processing the next element. The seed itself is not emitted. An empty source produces no values. A source failure propagates after prior outputs; started upstream work closes on completion, failure, or interruption. The backend uses Stream.mapAccum with a lazy seed and no onHalt callback. A source binding named mapAccumStream shadows the prelude operation.

foldStream(stream, seed, update) accepts a Stream<A,E,R>, a pure seed expression of type S, and an inline pure two-argument callback from (S,A) to S, with no failure or service channels. It is a terminal effectful expression returning S, failing with E, and requiring R. Constructing its Effect does not evaluate the seed or pull the source. Each execution evaluates the seed once before the first pull, calls update once per source element in order, and returns the final state. An empty source returns the seed. Each execution starts with fresh state. A source failure propagates without returning a state, and started upstream work closes normally on completion, failure, or interruption. The backend uses Stream.runFold with a lazy seed function. A source binding named foldStream shadows the prelude operation.

foldEffectStream(stream, seed, update) accepts a Stream<A,E,R>, a pure seed expression of type S, and an inline two-argument callback from (S,A) to S that may fail with E2 and require R2. It is a terminal effectful expression returning S, failing with E | E2, and requiring R | R2. Constructing its Effect does not evaluate the seed or pull the source. Each execution evaluates the seed once before the first pull, calls update sequentially once per source element, and returns the final state. An empty source returns the seed without calling update. Each execution starts with fresh state. A source or update failure stops later pulls and propagates; started upstream work closes on completion, failure, or interruption. The backend uses Stream.runFoldEffect with a lazy seed function and an Effect-valued callback, lifting a pure callback when needed. A source binding named foldEffectStream shadows the prelude operation.

Failure interrupts the other producer and waits for its finalizers. Buffer and merge combine deferred failure and requirement channels. Neither operation starts a producer before terminal consumption.

Retry schedules

RetrySchedule<E> is a first-class retry policy for nominal failure type E. retrySchedule takes a pure callback receiving the latest error and attempt number. The first failure has attempt number 1.

The callback returns Option<DelayMs>, where DelayMs aliases int and measures milliseconds. Some permits another attempt after that delay. None propagates the latest failure.

A negative delay is a runtime defect. retry(job, { schedule: policy }) keeps the job result, failures, and requirements. The existing { times: N } form remains valid. Defects and interruption are not retried.

Source codecs

Codec<Decoded,Encoded> is a value with two pure transformations. codec(decode, encode) infers its types from annotated callback parameters and results. Both types must have compiler-derived schemas.

decode(codec, input) accepts unknown and returns Option<Decoded>. encode(codec, value) returns Option<Encoded>. Invalid values produce None. Codec construction and both transformations have no failure or service channels.

Effectful transformations, recursive schemas, and arbitrary Schema values remain deferred. A required Option field remains distinct from an optional field during both directions.

Source Layers and host adapters

Layer<Services,E,R> is a deferred provider value. layer(Service, acquire) receives an inline acquisition callback that produces exactly the service methods. Its failures and requirements become acquisition channels.

mergeLayers(left, right) combines disjoint service sets and acquisition channels. An overlap is a type error. provide accepts both source Layer expressions and declared host providers.

Package implementations stay in TypeScript behind registered host modules. Adapters validate data boundaries, translate package failures into declared errors, and preserve requirement and lifetime contracts.

The first adapter targets a file operation from effect/FileSystem. Its host interface declares a specific expected error and any required service methods. The adapter translates package failures at the boundary.

Typed IR migration

Core 1 uses light-functional-ir version 2. The version 2 model adds Ref, Fiber, RetrySchedule, Codec, opaque types, borrow qualifiers, and the operations above. Each expression keeps active and deferred channels distinct.

The compiler rejects version 1 IR input with a version diagnostic. Existing fixtures and the linked model use version 2, including the core 1 nodes.

The independent validator must reject malformed type constructors, escaped borrowed identities, invalid concurrency scopes, unsound deferred channels, and Layer service overlaps before emission.

Raw Scope values, explicit Scope.close, effectful codecs, general Schedule operators, and direct package imports remain outside core 1.
